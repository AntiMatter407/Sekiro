# Bug/问题修复工作流规则

> 分析未知的 Bug、问题、错误时，必须先给出分析结果，等待用户确认后再执行修改。

## 规则

1. **先分析，后修改** — 遇到**未知的** Bug/问题/错误/报错/异常行为时，必须先给出完整的根因分析，**不能直接修改代码或配置**。

2. **分析报告要求** — 分析结果必须包括：
   - 问题现象（实际表现 vs 预期表现，附相关日志/截图/报错信息）
   - 根因分析（哪个文件、哪行代码、什么逻辑导致）
   - 修复方案（改什么、怎么改、涉及哪些文件）
   - 风险评估（修改是否会影响其他功能）
   - 修复步骤（按优先级排序列出）

3. **确认流程** — 分析报告给出后，等待用户回复确认再执行修改。用户可能：
   - 要求补充分析细节
   - 调整修复方案/范围
   - 确认后修改

4. **"未知"判定** — 以下属于"已知"，可以直接处理无需等待：
   - 用户明确要求"直接修改"或"不用确认"或"直接改"
   - 阻断编译的语法错误（如缺少分号、括号不匹配）— 这类问题根因明确不需要分析
   - 重复性/已知问题的固定修复模式（如之前反复确认过的同类崩溃修复）
   - 仅仅是打字错误/拼写错误（变量名写错、路径写错等，肉眼可见的笔误）
