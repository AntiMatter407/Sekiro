# /plan — 方案设计与任务拆分

## 触发方式

| 命令 | 作用 |
|------|------|
| `/plan <需求描述>` | 分析需求，设计方案，拆分为任务树 |
| `/plan list` | 列出 `Docs/plan/` 中所有需求及状态 |
| `/plan <名称>` | 打开指定需求文档，恢复/继续/修改该需求 |

`<名称>` 匹配 `Docs/plan/` 中的文件名（不含 `.md`），支持模糊匹配。

## 工作流

```
/plan <需求描述>
      │
      ▼
  1. 读取项目上下文（CLAUDE.md、directory-structure.md）
  2. 探索相关代码，确认现状
  3. 设计实现方案
  4. 拆分任务树（自顶向下）
  5. 用户确认 → 写入文档
```

## 文档模板

在 `Docs/plan/<slug>.md` 创建：

```markdown

| 状态 | 创建 | 更新 |
|------|------|------|
| 🔴 未开始 | YYYY-MM-DD | YYYY-MM-DD |

## 需求描述
（用户原始需求 + AI 理解确认）

## 方案设计
（实现思路、模块划分、关键接口、数据流）

## 涉及文件

| 文件 | 操作 | 说明 |
|------|------|------|
| Source/Sekiro/Combat/SKCombatComp.h | 修改 | 新增 XXX 方法 |

## 任务树
```

## 方案设计原则

1. **先探索再设计** — 搜索涉及模块的现有代码，确认现状和模式
2. **明确文件范围** — 列出每个任务涉及的具体文件及操作（新建/修改/删除）
3. **接口先行** — 关键函数签名、类结构在方案中明确
4. **数据流清晰** — 模块间数据如何流转、谁负责什么

## 拆分原则

1. **自顶向下** — 先拆顶层任务，用户确认后再递归拆分子任务
2. **依赖明确** — 每个任务标注依赖关系，形成 DAG
3. **可验证** — 每个叶子任务有明确完成标准
4. **单任务聚焦** — 一次只推进一个子任务，完成后再下一个

## 确认机制

1. AI 分析需求后，**先在对话中输出方案草稿 + 任务树**
2. 用户可以调整方案、增删改任务、修改依赖
3. 用户确认后，AI 写入 `Docs/plan/<slug>.md`
4. 后续修改时，同样先展示变更 → 确认 → 再写入

## 操作规则

- **每次操作后**自动更新文档的「更新」日期和「变更记录」
- **状态切换**：⬜ → 🔄（开始）→ ✅（完成）/ ❌（取消）
- **任务变更**：增删改任务时，在变更记录中注明
- **完成不删除**：状态改为 ✅ 已完成，文档保留
- **继续旧需求**：通过 `/plan <名称>` 打开，可在原文档上修改、追加、重启

## 执行规范

### `/plan list` 固定步骤

```
1. Glob path="Docs/plan" pattern="**/*.md"
2. 遍历结果，用 Read 读取每个文件头几行提取状态
3. 按格式输出
```

### `/plan <名称>` 固定步骤

```
1. Glob path="Docs/plan" pattern="{名称}.md"
   未命中时模糊匹配：Glob path="Docs/plan" pattern="**/*.md"，找名称相似的文件
2. Read 匹配文件，输出任务树和状态
```

### 写入路径

所有 plan 文档统一写入 `Docs/plan/`。
